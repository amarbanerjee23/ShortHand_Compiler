## Purpose

GitHub PR99 implements the release-candidate control plane for the bounded
enterprise pilot. It combines the original roadmap PR96 pilot/RC exit with the
audit-derived PR99 CPU-scope decision. The contract makes install, upgrade,
rollback, deployment, soak, disaster-recovery, security and evidence checks
executable and aggregates their blockers without converting an unavailable
dependency or open evidence row into release success.

This is a release-candidate gate implementation, not an enterprise GA claim.
The aggregate can pass as an auditable **blocked** decision while the repository
remains `controlled_beta`. A blocked decision is the expected result until all
declared production blockers are closed by later work or an external protected
release exercise.

## Declared CPU scope

The only production-supported tuple in this contract is:

| Field | Value |
| --- | --- |
| Scope | `linux-x64-cpu-v1` |
| Backend | `onnxruntime_cpu` |
| Device | CPU |
| Live fixture | pinned identity ONNX model and PR98 family probes |
| Fallback | never counted as executed inference |
| GPU/TPU/NPU | inventory-only; not production-supported |

An accelerator SDK, detected device or experimental override cannot satisfy the
CPU release-candidate gate. Expanding the support set requires a separate
versioned contract and live device-backed numerical evidence for every new
backend/device/platform tuple.

## Required release-candidate evidence

The aggregate executes or consumes these independent controls:

1. clean CMake install into an isolated prefix and a downstream installed SDK
   consumer;
2. same-version reinstall as an idempotent upgrade, with byte-for-byte
   installed-manifest comparison;
3. transactional candidate activation and rollback to the previous verified
   candidate, with checksum and scope validation;
4. the existing native serving cancellation, bounded-load and soak checks;
5. the inherited hardened container and ephemeral Kubernetes deployment gate,
   including readiness, restart, quota, default-deny network and graceful
   drain evidence;
6. existing sanitizer, race, security, SBOM, provenance, portability,
   reproducibility, C3-ECO and live ONNX gates; and
7. a deterministic report listing every partial/open production blocker and
   the exact contract decision.

The RC script never treats a source declaration as execution evidence. In CI,
the execution form receives the already-built CMake tree and runs the full
install/reinstall/uninstall lifecycle plus the rollback transaction probe. The
contract-only form is used by governance and negative tests to validate the
machine-readable policy without manufacturing runtime evidence.

## Lifecycle and rollback boundary

Candidate releases are staged under an isolated temporary root. Activation is
allowed only after the candidate manifest declares this exact contract,
`production_claim:false`, and `accelerator_production_support:false`. The
active pointer changes atomically after checksum verification. A failed health
or contract check leaves the previous pointer untouched; an explicit rollback
restores that pointer and revalidates its manifest. The probe does not mutate a
repository checkout or a user-selected broad directory.

The installed SDK lifecycle uses the repository's CMake install manifest:

- a fresh build must contain generated `cmake_install.cmake` rules and the built
  compiler; `install_manifest.txt` is generated by the first install, not required
  before it;
- install and downstream consumer build must succeed;
- reinstall must produce the same manifest hashes;
- uninstall removes the recorded files; and
- a consumer configure after uninstall must fail for the missing ShortHand
  package, not for an unrelated toolchain error.

## Blocker aggregation

The report schema is `schemas/enterprise_pilot_rc_v1.schema.json`, and the
machine-readable scope is `docs/production_rc_scope.tsv`. The report contains
separate compiler-matrix and C3-ECO traceability blocker arrays. This keeps the
remaining calibrated physical comparison, lifecycle/cloud, independent review,
and protected-release work visible. It is invalid for a release decision to
claim `eligible_for_release` while either array is non-empty.

PR99 closes the implementation gap for TST027 (the zero-skip RC gate) by
requiring a report and regression tests. It does not close TST017, TST025 or
TST026, and it does not close the C3-ECO lifecycle and independent-certification
evidence that belongs to PR100-PR102.

## Claim boundary

This contract does not claim universal energy superiority, lowest-carbon
software, complete standard-dataset coverage, official C3-ECO certification,
public authenticated ingress or accelerator production support. Candidate
reports remain evidence for controlled review only. Any future public claim
must name the workload, comparator, hardware, quality/SLO guardrails,
measurement boundary, uncertainty and retained evidence.
