# ShortHand beta-0.3 executable semantics

execution_semantics_contract: beta-0.3-pr72-v1
language_syntax_version: beta-0.3
semantic_differential_schema: shorthand.semantic.differential.v1
production_claim: false

This document defines the observable core-language execution contract introduced by PR72. It does not add syntax. Parser acceptance remains governed by the beta-0.2 base grammar plus the beta-0.3 module extension. A parser-valid construct is not automatically executable; unsupported execution must fail explicitly rather than being silently coerced into a different meaning.

## Observable execution result

For a conforming executable core program, ShortHand compares three modes:

1. interpreter execution with `short_hand source.short run`,
2. LLVM bitcode generated by `compile-bc` and executed with `lli`,
3. a native binary generated by `compile-native`.

The differential contract compares successful stdout exactly against a checked-in golden result. Failures compare non-zero exit category and stable `SHD` diagnostic code. Source presentation may differ for generated machine code, but a runtime failure must never become a signal crash, sanitizer report or false success.

## Executable primitive values

The PR72 core execution contract supports:

- `int` as a signed 32-bit two's-complement value,
- `bool` as a logical value represented observably as `0` or `1`,
- fixed-size arrays of executable scalar values.

The parser also accepts `float`, `double`, `string` and `void` in primitive declaration positions. Those historical syntax tokens are not silently treated as integers. Primitive variables, arrays, parameters or non-void function results that do not yet have an honest representation in all three engines fail with `SHD3003`. `void` remains valid as a function return type.

AI tensor/model precision types are governed by the AI runtime contract and are not reclassified by this primitive-language boundary.

## Integer arithmetic

Addition, subtraction and multiplication use deterministic 32-bit two's-complement wrapping semantics. This matches LLVM integer operations and avoids dependence on host C++ signed-overflow behavior.

Division and remainder are signed integer operations. Division/remainder by zero and the `INT_MIN / -1` signed overflow case are language runtime errors and fail with `SHD7001` before LLVM performs an invalid operation.

Comparisons produce `0` or `1`. Logical `&&` and `||` treat zero as false and non-zero as true.

## Variables and arrays

Global primitive declarations are zero-initialized. Function parameters live in a call frame and shadow globals with the same name if a future valid program permits such a name; graph-wide linker-visible collisions remain independently rejected by the module resolver where applicable.

Every scalar or array reference must resolve during semantic analysis. An unresolved name fails with `SHD3008`.

Array indices are signed integer expressions. An index below zero or greater than or equal to the declared length fails deterministically with `SHD7002` in interpreter, LLVM bitcode and native execution.

## Functions

Function declarations register callable definitions; declaration traversal never executes a function body.

Function calls use positional value parameters. The number of arguments must exactly match the declared parameter count or semantic analysis fails with `SHD3004`. Array parameters are outside the PR72 executable contract and fail explicitly instead of decaying to host pointers.

Each call creates an isolated parameter frame while retaining access to program globals. Nested and recursive calls are supported up to a deterministic implementation call-depth ceiling; exceeding that ceiling is a runtime invariant failure.

`return expression;` evaluates the expression and immediately exits the current function. `return;` exits with the default observable integer result `0` for the current beta contract. Returning a value from a `void` function fails with `SHD3007`. `return` at top level fails with `SHD3005`.

The current beta-0.3 grammar exposes function calls as statements with variable arguments, not as general expressions. PR72 implements internal call-expression visitors defensively but does not activate new syntax or change the language version.

## Modules and imported calls

PR70's `shorthand.package.v1`, `shorthand.lock.v1`, deterministic graph ordering, package confinement and source identity validation remain authoritative.

For an entry module, only functions declared in its direct imports are semantically visible, consistent with the existing module visibility contract. Imported program declarations and functions are loaded into the execution environment, but imported top-level logic is not executed as entry-point code. The entry module remains the sole program entry point.

The historical `SHD2030` code is retained for compatibility documentation but normal beta-0.3 imported calls are no longer rejected when the locked module graph validates successfully. The PR70 native fixture is now required to produce the same interpreter and native stdout.

## Branches and loops

`if` and `if/else` evaluate zero as false and non-zero as true.

The counted loop form evaluates the current step each iteration. A positive step continues while the loop variable is less than the bound; a negative step continues while it is greater than the bound. A zero step fails with `SHD7003` instead of hanging.

`continue` transfers to the counted-loop step operation or to condition reevaluation in a condition loop. `break` exits the nearest loop. `return` propagates out of all enclosing blocks and loops to the active function call.

`break` or `continue` outside a loop remains a semantic error (`SHD3001`, `SHD3002`).

## Goto boundary

`goto` remains parser-valid for compatibility with the beta-0.2 syntax contract, but the previous interpreter and LLVM implementations did not share correct label/jump semantics. PR72 therefore fails `goto` execution with `SHD3006` before either engine runs it. This is an honest boundary, not a removal of parser compatibility. A future language version may define and implement identical jump semantics or formally deprecate the construct.

## Deterministic runtime failures

| Code | Meaning |
| --- | --- |
| `SHD7001` | Arithmetic domain error for signed division/remainder |
| `SHD7002` | Array index outside declared bounds |
| `SHD7003` | Zero counted-loop step |
| `SHD7004` | Internal runtime invariant failed after semantic validation |

A runtime-negative differential test passes only if interpreter, `lli` and native execution all terminate non-zero with the expected stable code and without sanitizer/crash markers.

## Differential evidence

`scripts/check_semantic_differential.sh` is the executable guard. It includes:

- a checked-in golden core-control fixture covering functions, nested calls, early return behavior, boolean branching, arrays, counted loops, condition loops, `break` and `continue`,
- semantic-negative fixtures for unsupported executable types, arity, return context/type, undeclared names and the `goto` boundary,
- runtime-negative fixtures for arithmetic domains, array bounds and zero loop steps,
- exact interpreter/`lli`/native success-output comparison,
- machine-readable result artifact `shorthand.semantic.differential.v1`.

PR72 does not claim full backend/hardware numerical qualification, fuzz/race completeness, multi-platform reproducibility, MLIR equivalence or energy superiority. Those remain governed by later production-readiness PRs.
